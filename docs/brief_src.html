2. How each component works

  • Ingestion: Repairs UTF-8 BOM/UTF-16/cp1252 mojibake, sniffs CSV/TSV/│-box dialects, parses nested/coded/stringified JSON, FHIR R4, HL7 v2, and notes; streams files >2 MB with bounded memory and quarantines symlinks, binaries, or >64-deep JSON without raw copy.
  • Multilingual detection: Schema lexicons + value-shape inference + pyDeid/Philter/medSpaCy clinical context rules (Addison's, CPAP, Dr./SN, C/O/S/O complaints, Bharti No vs admission) across English, Hindi, Hinglish, and 10 Indic scripts (\u0900–\u0DFF).
  • Identity linkage & keyed pseudonyms: Links patients across files/scripts via Scalar-first inverted blocking, Odia/Assamese/Devanagari phonetic skeletons, honorific removal, and whole-cluster cannot-link checks (gender, compatible birth year, Aadhaar/ABHA/PAN). Emits deterministic 50-bit Crockford Base32 PSN-XXXXXXXXXX via HMAC-SHA256(RAKSHA_SECRET, "psn|" + key).
  • Adaptive privacy policy: Pools each patient's quasi-identifiers across all records and applies ARX minimal-loss k_dist (width-5 band with district drop at k≥5 before 10-year widening) plus rare-ICD (≤3) / age ≥80 escalation and consistent per-patient HMAC date shifts (±180d) keeping clinical LOS and order exact.

3. USP & Security design (encryption at rest)

  • USPs: (1) Pooled longitudinal ARX privacy over linked multi-file patients rather than naive single-row masking; (2) Zero-false-merge cluster firewall beating generic Splink-TF (FM=0 vs 105–2,902); (3) Pure Python 3.10+ stdlib (0 LLMs/ML bloat); (4) Assurance 3.0 release verifier (tools/veil_passport.py).
  • Security & encryption at rest: Official runtime (main.py) keeps all raw inputs and linkage graphs strictly ephemeral in process RAM (freed between passes)—zero persistent unencrypted raw intermediates are written to disk, TMPDIR, or HOME. Only already-sanitized files (sanitized/.veil_tmp_* → os.replace), pseudonym locators (records.jsonl), and non-PII report.json hit disk. RAKSHA_SECRET is env-only, required non-empty at startup (exit 2 if missing), never logged, and separated cleanly from storage. UI dev uploads are held only ephemerally and wiped immediately after execution.

5. Runtime, memory scaling & Assurance Engine 3.0

  • Resource headroom (<4,096 MB / <900s, 2 CPU target): Scalar-first Linker & early text release cut RSS across every tier: 100k_unique in 12.38s / 516.9 MB, 500k_repeat in 55.59s / 1,766.6 MB, 1M_repeat in 113.16s / 3,206.6 MB, 1,000,000 distinct patients in 128.93s / 3,176.2 MB (7,756 rows/s, 0 collisions), and 1.25M mixed (6,252 files, 943,750 records) in 682.76s / 2,928.4 MB.
  • Assurance Engine 3.0 (tools/veil_passport.py, 39/39 tests, 180/180 Hypothesis properties): Truth-free audit passes all 5 checks on dev: structural 200/200, privacy 197/197 (distinguishes 40 facility strings without whitelisting contaminated IDs), clinical 2361/2361, temporal 724/724 (48/48 patient chronology), identity 774/774.

6. Honest limitations

  • Adversarial & clinical boundary: Tested against ATTACKS.md and local invariants on macOS Python 3.14 (host Docker daemon inactive); no empirical check proves anonymity outside that attacker model, and preserving rare ICD-10 codes + exact LOS keeps rare-profile A5 non-zero.
  • Conservative linkage & substring false positives: Unsupported non-Indian scripts and ambiguous unlinked singletons abstain cleanly (0 false merges); local substring audits still flag preserved doctors (Dr.) or lab digits overlapping patient keys rather than erasing medical data.
