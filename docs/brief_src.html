1. What VEIL is

VEIL is a clinical privacy release-assurance engine for fragmented, multilingual Indian hospital exports (CSV/TSV, nested JSON, JSON Lines, FHIR R4, free-text notes in Latin, Devanagari and Hinglish). It does not mask documents one at a time. It first resolves each patient's records across files, scripts and hospitals, then measures re-identification risk on the patient's pooled profile, which is the unit the attacker reconstructs, and generalises only the patients who stand out. An independent verification pass and a truth-free Privacy Passport audit check the release before it ships. No LLMs, no ML models, no network.

2. Architecture (two passes)

input/ ─► 1 Ingest: encoding + dialect sniffing, depth/time budgets, symlink/binary/malformed quarantine (never copied raw)
       ─► 2 Structure: field kinds from EN/HI/regional label lexicons + value shape; patient records at any depth
            (nested arrays, keyed maps, header+rows, pairs); identifier-style schema keys never treated as names
       ─► 3 Harvest: names / IDs / phones / places from structured fields + labelled, kinship, honorific and contextual cues
       ─► 4 Identity graph: strong IDs and household-aware phones, then name skeleton (script-independent) + second clue,
            accepted only with a clear margin; whole-cluster cannot-link (gender, DOB, age, national-ID conflicts,
            tolerant of one-digit entry typos); passes re-run to a fixpoint; HMAC-SHA256 pseudonyms
       ─► 5 Pooled-profile privacy: release-level equivalence classes + rare-condition / age≥80 escalation; truthful
            per-patient consistent bands; per-patient secret date shifts (intervals and stay lengths exact)
       ─► 6 Rewrite: clinical and doctor spans protected first; hidden channels (keys, headers, filenames, metadata, base64)
       ─► 7 Verify: independent exact-substring sweep of harvested identifiers ─► sanitized/ + report.json + records.jsonl
offline audit (not in runtime): tools/veil_passport.py — structural, privacy-residue, clinical/interval, identity checks

3. Distinctive engineering (and what we adapted)

  • Pooled longitudinal privacy — risk is assessed per resolved patient, not per record. Adapted from ARX's risk-driven anonymisation (attacker models on structured tables). Our contribution is applying it to pooled multilingual free text plus structured records offline.
  • Zero-false-merge identity graph — Fellegi–Sunter-style weighted evidence with term-frequency weights and blocking (inspired by Splink/Dedupe), plus whole-cluster cannot-link invariants so two plausible links cannot chain different people.
  • Clinical-first scrubbing — protected spans before redaction (Philter-style recall-first design; Presidio-style context cues).
  • Release assurance — an in-engine verification sweep, plus an offline Passport that audits a release with no ground truth.

6. Security and compliance

  • RAKSHA_SECRET is only an HMAC key and is never written. Pseudonyms, shifts and renamed keys/files are keyed and non-reversible. Output is deterministic per secret and changes with a different secret.
  • Fail-safe: per-file time budget, bounded regexes, depth guard and symlink refusal. Anything unsafe is quarantined, never copied raw. Exports are contained inside sanitized/.
  • Adversarial suite: {{TESTS}} unit/contract/fuzz/regression tests; 100k-row runs in about 11 s and under 0.7 GB; worst-case linkage scenarios with 0 false merges.

7. Limitations (honest)

  • All scores here are a local re-implementation of the published scorer and attacker on synthetic data. The official evaluator is sealed. No finite test proves anonymity, and defeating one attacker model does not prevent others.
  • Escalated high-risk patients lose DOB and fine geography (district may be dropped for small classes): a measured privacy-over-utility trade-off.
  • When a JSON key is itself PII (a map keyed by MRN or name), emitting the contract's input locator would leak it into records.jsonl. VEIL reports the nearest safe ancestor instead (no identity credit for those records), pending organiser clarification.
  • Names with no structural or contextual cue can survive. The verifier only catches values harvested elsewhere in the release.
